## 1. Hypothesis

> The breakout strategy's research edge survives the transition from historical backtest to real-time live execution on a MetaQuotes demo account, despite real broker spreads, real execution latency, real slippage, and actual fills.

### What we are NOT testing

- Whether the strategy is profitable in absolute terms (S6 already answered this)
- Whether we can optimize live P&L
- Whether the strategy works better live than in backtest
- Whether the strategy is suitable for production deployment

### What we ARE testing

- Whether the S6 edge **survives** the transition to live execution
- The **magnitude of degradation** from research conditions to live conditions
- Whether degradation is **explainable** (spread, slippage, latency) or **unexplained** (edge disappearance)
- Whether the execution infrastructure can **reliably capture** what the strategy signals

### Pass/Fail Criteria

| Criterion | PASS | WARN | FAIL |
|-----------|------|------|------|
| Signal fidelity | ≥95% signals correctly identified | 90-95% | <90% |
| Fill rate | ≥90% signals result in fills | 80-90% | <80% |
| Avg slippage | ≤0.5 pip average | 0.5-1.0 pip | >1.0 pip |
| Win rate | Within 5pp of S6 baseline (35.7%) | 5-10pp deviation | >10pp deviation |
| Profit factor | ≥1.5 | 1.0-1.5 | <1.0 |
| Avg PnL per trade | ≥+10 pip | +5 to +10 pip | <+5 pip |
| Execution errors | ≤5% of signals | 5-10% | >10% |

**Overall assessment:**
- All criteria PASS → edge survived intact
- Any WARN → edge degraded but explainable
- Any FAIL → edge compromised, investigate root cause

## 4. Experiment Timeline

### Pre-Experiment (Day -3 to Day 0)

1. Verify MT5 API returns correct account info
2. Verify MT5 API returns correct symbol data
3. Run signal generator in shadow mode (compute signals but don't trade)
4. Compare shadow signals against S6 backtest signals for 48 hours
5. Verify all data capture fields are being recorded
6. Run end-to-end order submission test (submit and immediately cancel)
7. Verify trade log writes correctly
8. Verify health monitor detects disconnections
9. Document baseline live spread for each pair

### Experiment Start (Day 0, 00:00 UTC)

**The 2-week clock starts when:**
- All pre-experiment checks pass
- The first real signal is generated AND results in a live order
- The experiment start timestamp is recorded

**The 2-week clock ends:**
- 14 calendar days after the first live order
- NOT 14 calendar days after the first signal (signals without orders don't count)

### During Experiment

- Strategy runs 24/5 (Forex market hours)
- No manual intervention unless infrastructure fails
- Daily health check logged
- Weekly performance summary generated

### Post-Experiment (Day 15 to Day 21)

1. Freeze all trade logs
2. Generate S7 comparison report
3. Compare S6 vs S7 metrics
4. Document all anomalies
5. Write S7 conclusion

## 5. Failure Handling

### 5.1 MT5 Disconnection

| Duration | Action |
|----------|--------|
| < 5 minutes | Log event, no action, continue |
| 5-30 minutes | Log event, check if any signals missed, continue |
| 30-60 minutes | Log event, document missed signals, attempt reconnect |
| > 60 minutes | Log event, document missed signals, restart MT5, verify API |
| > 4 hours | Log event, document all missed signals, consider experiment compromised |

**Decision rule:** If total disconnection time exceeds 10% of experiment duration, the experiment is INVALID for that period.

### 5.2 Trade Rejection

| Rejection Type | Action |
|----------------|--------|
| Insufficient margin | Log, reduce position size, retry |
| Invalid price | Log, wait for next bar, continue |
| Market closed | Log, skip signal, continue |
| Unknown error | Log, attempt retry once, if fail skip signal |

**Decision rule:** If >10% of signals result in rejections, the experiment is INVALID.

### 5.3 Partial Fills

| Fill Percentage | Action |
|-----------------|--------|
| ≥80% filled | Accept fill, record partial |
| 50-80% filled | Accept fill, record partial, flag for review |
| <50% filled | Reject fill, log as rejected, skip signal |

### 5.4 Infrastructure Failure

If the Docker container crashes:
1. Restart container (auto-restart: unless-stopped)
2. Wait for MT5 to reconnect (up to 5 minutes)
3. Verify API health
4. Log the event
5. If recovery < 15 minutes: continue experiment
6. If recovery > 15 minutes: document missed signals, continue
7. If recovery > 4 hours: experiment may be compromised

## 7. Manual Intervention Rules

### Permitted

- Fixing infrastructure (restart container, restart MT5)
- Investigating anomalies (checking logs, reviewing trades)
- Documenting observations

### Prohibited

- Modifying strategy parameters during the experiment
- Cancelling pending orders without infrastructure justification
- Adjusting position sizes beyond the predefined rules
- Manually overriding trade entries or exits
- Adding new filters or conditions

**Rationale:** This is a scientific experiment. Any modification invalidates the comparison against S6.

## 8. Data Integrity Rules

### Valid Data

- All fields in sections 3.1-3.6 are populated
- Timestamps are monotonic within each record type
- Signal IDs link correctly to order IDs and fill IDs
- PnL calculations match fill prices and exit prices

### Invalid/Corrupted Data

A trade record is INVALID if:
- Missing fill price or exit price
- Timestamps are inconsistent (exit before entry)
- PnL doesn't match price difference
- Order was submitted but no fill record exists
- Fill exists but no signal record exists (orphan fill)

**Decision rule:** If >5% of trade records are invalid, the experiment is COMPROMISED.

### Reconciliation

At experiment end:
1. Count signals generated vs orders submitted (should match)
2. Count orders submitted vs fills received (fill rate)
3. Count fills vs exits (all positions must close)
4. Verify net PnL matches sum of individual trade PnLs
5. Verify no orphan records exist

## 9. Missed Signals

### Do they count?

**Yes, partially.** Missed signals due to infrastructure failure count as a NEGATIVE data point for execution viability. They don't count as trading losses (no money was lost), but they reduce the effective signal count.

### Classification

| Missed Signal Cause | Counts Against Viability? |
|--------------------|-----------------------------|
| MT5 disconnected | YES — infrastructure failure |
| API timeout | YES — infrastructure failure |
| Signal generated but not submitted (bug) | YES — implementation failure |
| No valid signal during bar (research accuracy) | NO — expected behavior |
| Market closed | NO — expected behavior |

## 12. Implementation Dependencies

The execution adapter must implement (derived from this protocol):

1. **Signal generator**: Real-time swing level detection on 4h bars
2. **Order manager**: Submit market orders to MT5 via API
3. **Position tracker**: Monitor open positions, manage SL/TP/trailing
4. **Trade logger**: Record all fields from sections 3.1-3.6
5. **Health monitor**: Detect disconnections, log infrastructure events
6. **Risk guard**: Enforce exposure limits from section 6
7. **Report generator**: Daily/weekly/final reports per section 10

**Nothing more.** The adapter implements exactly what this protocol requires. No additional features, no optimization, no dynamic parameter adjustment.
