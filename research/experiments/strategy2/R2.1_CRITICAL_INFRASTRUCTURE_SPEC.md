### Status: OPEN DECISION — Requires Approval

### Analysis of Existing Regime Code

The repository contains regime classification infrastructure in `research/shared/regime/`:

| File | Purpose | Lines |
|---|---|---|

| `research/shared/regime/tabfm/predictor.py:39-199` | TabFM neural detector | 199 |

### Existing Regime Labels (from `labels.py:10-31`)

```
TRENDING, RANGING, BREAKOUT, HIGH_VOL, LOW_VOL, MEAN_REVERSION, NEWS_DRIVEN, UNKNOWN
```

### R2.1 Robustness Target (from ROS §13)

> «2/3 of predefined regimes»

### R2.1 Experiment Design (from `R2.1_EXPERIMENT_DESIGN.md:204-206`)

> "Classify periods as low/medium/high vol. Report per-regime results."

### Assessment: Not Directly Reusable

The existing regime classifiers are **not applicable** to R2.1 for three reasons:

1. **Wrong taxonomy.** The existing labels (TRENDING, RANGING, BREAKOUT, etc.) are trading-strategy regimes. R2.1 needs volatility regimes (low/medium/high vol) as specified in the experiment design. These are different constructs.

2. **Wrong dependency chain.** `adx_regime.py:9` imports `from nestquant.core.tooling.indicators.adx import calculate_adx`. This violates the isolation boundary rule (A4.1) — research must not import from `core/`.

3. **Wrong purpose.** The existing detectors are designed for real-time strategy selection (single prediction per bar). R2.1 needs historical regime labeling for robustness analysis (label every bar in a time series). The `predict(pair, features_df)` interface returns a single `RegimePrediction` for the last bar, not a full time-series classification.

### Required Resolution

R2.1 needs a regime classifier that:
- Uses a volatility-based taxonomy (low/medium/high vol)
- Is causally safe (label at bar t uses only data up to bar t)
- Produces a full time-series of regime labels (not single predictions)
- Does not depend on production code
- Has its own independent tests

**Decision required:** Should R2.1:
- **(a)** Define its own simple volatility-regime classifier (e.g., rolling vol terciles) — recommended, minimal, self-contained
- **(b)** Adapt the existing regime framework with a new VolatilityRegimeDetector class in `apparatus/`
- **(c)** Defer regime analysis entirely and mark the 2/3-regimes robustness target as NOT_EVALUABLE until a regime definition is approved

**This document does NOT resolve this decision.** It is flagged under item 12 (Open Decisions).

> **OPEN DECISION — DEFERRED TO STAGE 3: Regime-label methodology**
>
> Even after Option (a) (rolling-volatility terciles) is selected as the regime family, a further decision remains: whether regime labels are **fold-relative** or **globally predeclared**.
>
> - **Fold-relative:** Each training fold computes its own `q33`/`q67` thresholds, making labels fold-specific and not directly comparable across folds. This is causally safe (uses only past data for thresholds) but makes cross-fold regime consistency harder to interpret.
>
> - **Globally predeclared:** Thresholds fixed once from an explicitly designated reference period, giving one comparable label set across the whole study but requiring justification for why using that reference period doesn't leak information.
>
> This must be resolved in Stage 3 before the "2/3 of predefined regimes" robustness target (and the "regime consistency" metric, already marked provisional pending B9) can be operationalized.

### Impact on This Specification

- Section H (Metric Contract): The `regime_consistency` metric is marked **PROVISIONAL/BLOCKED** pending B9 resolution.
- Section G (Validation Contract): Regime-conditioned evaluation is deferred.
- The remaining robustness targets (50% pairs, 50% windows) are unaffected.

## C. Data Contract

### C1. Canonical Timestamp Convention

- **Timezone:** UTC (always)
- **Index type:** `pd.DatetimeIndex` with `tz='UTC'`
- **Resolution:** Second-level precision stored, bar-level alignment for 4H bars
- **Bar timestamp semantics:** The timestamp marks the **end** of the bar period. A bar timestamped `2026-01-01 04:00:00 UTC` contains OHLCV data from `00:00:00` to `04:00:00 UTC`.

### C2. Bar Semantics (4H)

- **Frequency:** Every 4 hours: 00:00, 04:00, 08:00, 12:00, 16:00, 20:00 UTC
- **Session boundaries:** Not enforced. 4H bars are continuous across sessions.
- **Weekend handling:** No bars generated for Saturday/Sunday. Gap from Friday 20:00 to Sunday 18:00 (Dukascopy server time, which is EST → 23:00 UTC Sunday) is expected and flagged as informational, not an error.

### C3. OHLCV Schema

| Column | Type | Constraints | Description |
|---|---|---|---|
| `open` | float64 | > 0 | Opening price |
| `high` | float64 | >= open, >= close | Highest price in bar |
| `low` | float64 | <= open, <= close | Lowest price in bar |
| `close` | float64 | > 0 | Closing price |
| `volume` | float64 | >= 0 | Volume (ticks or notional) |
| `spread` | float64 | >= 0 | Bid-ask spread (informational) |

### C4. Missing-Bar Behavior

- **Missing bars are detected, not imputed.** A gap in the expected 4H sequence is recorded as a gap.
- **Gap classification:**
  - Weekend gap (44-76 hours): Expected, informational
  - Holiday gap (76-120 hours): Expected, informational
  - Runner gap (< 44 hours): Informational
  - Data corruption gap (> 120 hours): Flagged for investigation
- **Impact on models:** Missing bars are preserved as missing temporal observations and are never imputed. Model eligibility and temporal diagnostics must account for gaps explicitly. No model in the current family is assumed to natively understand irregular time spacing — gap handling is the responsibility of the data/feature layer, not the model layer.

### C5. Weekend Behavior

- Dukascopy 4H data: No Sunday bars, Saturday bars end at 20:00 EST (23:00 UTC)
- Decoded data: Sunday 18:00 UTC to Friday 20:00 UTC (no weekend bars)
- This is operational, not a defect.

### C6. Duplicate Handling

- **Duplicate timestamps are validation failures.** If `df.index.duplicated().any()` is True, the dataset status is `NOT_VALIDATED` and it does not proceed past Gate 1.
- **Deduplication is never a silent default.** If deduplication is later justified for a specific dataset, it must happen as an explicit, separately documented normalization step with deterministic, auditable rules — not as a silent default inside ingestion.

### C7. Gap Detection

- Compute `gaps = df.index.to_series().diff()`
- Expected gap: `pd.Timedelta(hours=4)`
- Gaps > expected are classified per C4
- All gaps are recorded in the data validation report

### C8. Price Precision

- Raw Dukascopy: 5-digit precision (e.g., 1.12345)
- Canonical bars: Preserve full precision, no rounding
- Return computation: Use float64 throughout

### C9. Return Construction

- **Primary:** Log returns: `r_t = log(close_t / close_{t-1})`
- **Formula:** `compute_log_returns(close: Series) → Series`
- **Causality:** Uses only current and previous close. No future information.
- **Missing returns:** First bar has NaN return. Models must handle this.

### C10. Realized Volatility Definitions

**Primary (close-to-close):**
```
RV_t(window) = std(r_{t-window+1}, ..., r_t)
```

**Secondary (Parkinson):**
```
Parkinson_RV(window) = sqrt( mean( ln(H/L)^2 ) / (4 * ln(2)) )
```

**Forward target (for evaluation):**

> **OPEN DECISION — DEFERRED TO STAGE 3**
>
> The target definition `target_t(horizon) = std(r_{t+1}, ..., r_{t+horizon})` is undefined or degenerate at `horizon = 1`: with sample std (ddof=1) it is `NaN` (only one observation), and with population std (ddof=0) it is exactly `0`. Neither is a meaningful volatility target, which breaks the canonical horizon set `[1, 3, 6, 12]` at its first element.
>
> This definition must be removed and replaced in Stage 3 protocol. Candidate resolution (not selected here): defining realized variance/volatility consistently across all horizons via `RV_{t,h} = Σ_{i=1}^{h} r_{t+i}²` and `σ_{t,h} = sqrt(RV_{t,h})`, which reduces cleanly to `σ_{t,1} = |r_{t+1}|` at horizon=1.
>
> This is a methodological/target-definition decision for Stage 3 protocol, not an infrastructure detail.

This is shifted by `-horizon` in the series to align with forecast timestamp t.

### C11. Provenance Requirements

Every dataset must record:
- Source (Dukascopy)
- Retrieval timestamp
- Decoder version
- Transformations applied
- SHA-256 checksum of raw file
- Dataset version string (e.g., `dukascopy-4h-20p-2011-2026-v1`)

### C12. Data Versioning

- Raw data: Immutable after download. Version = checksum prefix.
- Canonical data: Immutable after construction. Version = source version + bar-construction version.
- Derived data: Recomputable from canonical. Not versioned separately.
- Experiment data: Version-controlled in git.

## D. Causality Contract

### D1. Core Causality Rule

For any forecast at time t:

```
forecast_t = f(X_{≤ t})
```

The model must never use `X_{>t}` directly or indirectly.

### D2. Leakage Categories and Prevention

| Leakage Type | Mechanism | Prevention | Test |
|---|---|---|---|
| **Future-data leakage** | Model sees returns after forecast time | Walk-forward loop enforces strict temporal ordering | `_test_walkforward_no_lookahead` |
| **Look-ahead bias** | Target variable available during fitting | Target is forward-shifted and compared only after target period elapses | `_test_forward_target_alignment` |
| **Normalization leakage** | Z-score uses future statistics | Normalize only on training window statistics | New test: `_test_normalization_causality` |
| **Feature leakage** | Features computed using future data | All features are backward-looking (rolling/historical windows only) | `_test_returns_causality`, `_test_rolling_vol_causality` |
| **Hyperparameter leakage** | Hyperparameters selected using OOS results | Hyperparameters are predeclared, not tuned on OOS | Test: `_test_hyperparameter_predeclaration` |
| **Regime-label leakage** | Regime labels contain future information | Regime labels at bar t use only data up to bar t | Deferred (see B9) |
| **Train/test contamination** | OOS data influences training | Strict temporal split: train_end < test_start | `_test_train_test_boundary` |

### D3. Causality Invariants (Existing Tests)

The following 10 tests from `causality_tests.py` must continue to pass:

1. `_test_returns_causality` — Modifying future closes does not change past returns
2. `_test_rolling_vol_causality` — Modifying future returns does not change past rolling vol
3. `_test_ewma_causality` — Modifying future returns does not change past EWMA vol
4. `_test_atr_causality` — Modifying future OHLC does not change past ATR
5. `_test_forward_target_alignment` — Forward target uses correct future window
6. `_test_naive_causality` — Naive forecast is purely from past data
7. `_test_garch_causality` — GARCH estimation uses only training data
8. `_test_train_test_boundary` — Train ends before test begins
9. `_test_walkforward_no_lookahead` — Walk-forward loop has no overlap
10. `_test_synthetic_causality` — Controlled validation on synthetic data

### D4. Additional Causality Tests (Required)

| Test | Purpose | Priority |
|---|---|---|
| `walk_forward_causality` | Asserts Partition A (primary causal walk-forward) never allows information from `X_{>t}` into a forecast at `t`. This is where the actual causality invariant is enforced and tested. | HIGH |
| `blocked_partition_assignment` | Asserts the blocked partition assignment (A/B alternation) is constructed as specified, deterministically, from the predeclared block sizes. | HIGH |
| `blocked_noncausal_labeling` | Asserts that every result produced from the blocked/Partition-B path is labeled `TEMPORAL_GENERALIZATION_DIAGNOSTIC` in its metadata and can never be emitted, stored, or reported as `CAUSAL_OOS`. | HIGH |
| Normalization causality | Feature normalization uses only training stats | HIGH |
| Bootstrap causality | Bootstrap resampling preserves temporal ordering | HIGH |
| Metric causality | Metric computation does not use future forecasts | MEDIUM |

### D5. Synthetic Data Causality Validation

The synthetic data generator (`generate_synthetic_ohlcv`) produces data with known volatility structure (GARCH parameters: omega=0.00001, alpha=0.05, beta=0.90). This allows:

1. Verifying that model forecasts are independent of future returns
2. Verifying that parameter estimation uses only training data
3. Verifying that the walk-forward loop produces correct train/test splits

## E. Model Contract

### E1. VolatilityModel Protocol

```python
class VolatilityModel(Protocol):
    """Protocol for all volatility models in R2.1."""

    @property
    def name(self) -> str:
        """Unique model identifier (e.g., 'GARCH(1,1)', 'HAR-RV')."""
        ...

    def fit(self, returns: pd.Series) -> None:
        """Fit model on historical returns.

        CAUSAL: uses only the provided returns. No future information.
        Must handle: empty series, series with NaN, series < minimum length.
        """
        ...

    def forecast(self) -> float:
        """Generate 1-step-ahead forecast.

        CAUSAL: uses only fitted state from last fit() call.
        Returns: non-negative float (volatility estimate).
        """
        ...
```

Each model class accepts configuration at construction time. Configuration is immutable after construction.

| Model | Configuration Parameters | Defaults |
|---|---|---|

| EWMAModel | `span: int` | 24 |

> **OPEN DECISION — DEFERRED TO STAGE 3**
>
> The HAR model component names "daily/weekly/monthly" may be misleading. At 4H bars: 6 bars = 1 trading day (correct), 30 bars = 1 trading week (correct), but 90 bars = 15 trading days, not one trading month (~22 trading days ≈ 132 bars using the block-size convention).
>
> Stage 3 must decide whether these HAR component windows are: (a) canonical parameters inherited from the existing implementation, kept as-is under different, non-calendar-implying labels; or (b) redefined to genuine daily/weekly/monthly temporal semantics consistent with the block-size convention.
>
> The 6/30/90 values are NOT changed in this document.

## F. Horizon Contract

### F1. Canonical Horizons

```python
HORIZONS = [1, 3, 6, 12]  # bars at 4H frequency
```

| Horizon | Bars | Hours | Description | NQTS Relevance |
|---|---|---|---|---|
| 1 | 1 | 4h | Next candle volatility | Intra-trade risk |
| 3 | 3 | 12h | Next trading session | Position sizing |
| 6 | 6 | 24h | Next day | Daily risk limits |
| 12 | 12 | 48h | 2-day horizon | Max hold period risk |

### F2. Horizon Units

- Horizons are specified in **bars** (not hours)
- Conversion: `hours = bars * 4`
- The horizon regression tests verify this mapping: `expected_hours = {1: 4, 3: 12, 6: 24, 12: 48}`

### F3. Forecast Timestamp Semantics

- Forecast at timestamp t predicts realized volatility over `[t+1, t+horizon]`
- The forecast is compared to the target **only after** the target period has elapsed
- In walk-forward evaluation, forecast at bar t is evaluated against returns from bars `[t+1, t+horizon]`

### F4. Target Construction

```python
target_t(horizon) = std(r_{t+1}, ..., r_{t+horizon})
```

Implementation: `realized_volatility_forward(close, horizon)` computes rolling std of log-returns over the forward window, then shifts by `-horizon`.

### F5. Alignment Rules

- Forecast index = timestamp of the bar at which the forecast is made
- Target index = same timestamp (but computed from future returns)
- Comparison is deferred until the target period elapses
- No forecast is compared before its target period is complete

### F6. Horizon Leakage Rules

1. The target for horizon h uses returns from `[t+1, t+h]` — never `[t, t+h]` or earlier
2. The forecast at time t uses only data up to and including t
3. Walk-forward loop: `for t in range(train_window, n - horizon, step)`
4. Target is never available during model fitting

### F7. Existing Horizon Tests (Must Remain Green)

The 7 tests in `test_horizon_encoding.py` verify:
1. `HORIZONS == [1, 3, 6, 12]`

## G. Validation Contract

### G1. Two Distinct Validation Frameworks

Per ROS §11, the R2.1 validation architecture has two components:

**Partition A — Causal Walk-Forward (Deployment-Relevant OOS)**

This is the primary validation. Results are deployment-relevant.

**Partition B — Blocked Temporal Generalization (Diagnostic Only)**

This is a complementary diagnostic. Results must NEVER be labeled "OOS" — they are "temporal generalization diagnostics."

### G2. Causal Walk-Forward (Partition A)

```python
def walk_forward_evaluate(
    returns: pd.Series,
    models: list[VolatilityModel],
    target_horizon: int,
    train_window: int,
    step: int = 1,
) -> WalkForwardResult:
    """Causal walk-forward evaluation.

    At each step t:
    1. Fit models on returns[t - train_window : t]
    2. Forecast next horizon's volatility
    3. Compare to realized vol over [t+1, t+horizon]
    4. Advance by step bars

    CAUSAL: train ends at t, forecast is for t+1 to t+horizon.
    No future data leaks into training.
    """
```

**Parameters:**
- `returns`: Full return series (pd.Series, DatetimeIndex UTC)
- `models`: List of fresh model instances (not pre-fitted)
- `target_horizon`: Forecast horizon in bars
- `train_window`: Number of past bars for training (must be >= max model minimum)
- `step`: Step size between forecasts (1 = every bar)

**Output:**
```python
@dataclass
class WalkForwardResult:
    forecasts: pd.DataFrame  # columns: timestamp, forecast, realized, model, horizon
    fold_metadata: list[FoldMetadata]  # per-fold training/OOS periods
    n_folds: int
    n_models: int
```

**Fold metadata:**
```python
@dataclass
class FoldMetadata:
    fold_index: int
    train_start: pd.Timestamp

    n_oos: int
```

### G3. Blocked Temporal Generalization (Partition B)

```python
def blocked_temporal_evaluate(
    returns: pd.Series,
    models: list[VolatilityModel],
    target_horizon: int,
    block_size: int,
    n_partitions: int = 2,
) -> BlockedResult:
    """Blocked temporal generalization diagnostic.

    Divides the data into blocks of size block_size.
    Creates n_partitions alternating IS/OOS assignments.
    Every block gets evaluated in both IS and OOS roles.

    IMPORTANT: This is NOT causal OOS.
    If future blocks train on data that includes earlier blocks' periods,
    this is a temporal generalization diagnostic, not a deployment simulation.
    """
```

**Block sizes (predeclared):**

R2.1 block sizes are fixed observation-count blocks, not calendar-period resampling. "Monthly" means exactly 132 four-hour bars (~22 trading days × 6 bars/day), not the bars falling within a calendar month. This convention applies wherever block sizes are referenced in this document.

```python
BLOCK_SIZES = {
    "weekly": 6 * 5,       # 30 bars (5 trading days × 6 bars/day)
    "monthly": 6 * 22,     # 132 bars (~22 trading days)
    "quarterly": 6 * 66,   # 396 bars (~66 trading days)
    "semiannual": 6 * 132, # 792 bars (~132 trading days)
    "annual": 6 * 264,     # 1584 bars (~264 trading days)
}
```

**Infeasibility handling:**
- If `n_bars / block_size < 3`: block size is NOT_EVALUABLE
- Record as NOT_EVALUABLE in the ledger
- Do not adjust block size to make it pass
- Do not silently skip — report explicitly

**Partition A/B assignment:**
```python
# Partition A: blocks 0,2,4 are IS; blocks 1,3,5 are OOS
# Partition B: blocks 0,2,4 are OOS; blocks 1,3,5 are IS
```

- `train_window >= 30` (minimum for GARCH estimation)

### H1. Metric Tiers

|---|---|

**Tier 5 — Operational**

| Metric | Definition |
|---|---|
| Computation time | Wall-clock time per fold |
| Convergence rate | Fraction of successful model fits |
| Memory usage | Peak memory during evaluation |

### H2. QLIKE Numerical Stability

QLIKE is numerically unstable when `f ≈ 0` (division blows up).

**Floor rule:** Apply a floor of `ε = 1e-8` to both forecast and realized values before computing QLIKE.

```python
def compute_qlike(forecast: np.ndarray, realized: np.ndarray, epsilon: float = 1e-8) -> float:
    """QLIKE with numerical floor.

    Floor rationale:
    - Volatility is strictly positive; values < 1e-8 are effectively zero
    - 1e-8 is orders of magnitude below any realistic 4H volatility
    - This prevents division-by-zero without distorting meaningful values
    """
    f = np.maximum(forecast, epsilon)
    r = np.maximum(realized, epsilon)
    return float(np.mean(np.log(f**2) + r**2 / f**2))
```

**Alternative considered:** Excluding zero-vol observations entirely. Rejected because it introduces selection bias (zero-vol periods are informative — they indicate market closure or extreme compression).

## I. Statistical Inference

### I1. Bootstrap Family

**Primary method:** Moving block bootstrap

Why block bootstrap:
- Preserves temporal dependence structure
- Time series have serial correlation; IID shuffling destroys this
- Block bootstrap maintains local structure while allowing resampling of blocks

**Why naive IID shuffling is inappropriate:**

IID shuffling assumes observations are independent. Financial time series have:
- Volatility clustering (autocorrelation in squared returns)
- Mean reversion (autocorrelation in returns)
- Regime persistence (periods of high/low vol)

IID shuffling destroys these structures, producing artificially narrow confidence intervals and inflated significance.

### I2. Block Bootstrap Implementation

```python
def moving_block_bootstrap(
    data: np.ndarray,
    block_size: int,
    n_bootstrap: int = 1000,
    seed: int | None = None,
) -> np.ndarray:
    """Moving block bootstrap for dependent time series.

    Steps:
    1. Divide data into overlapping blocks of size block_size
    2. Randomly select n_bootstrap blocks (with replacement)
    3. Concatenate selected blocks
    4. Trim to original length

    Args:
        data: 1D time series
        block_size: Block length (must be >= 1 and <= len(data))
        n_bootstrap: Number of bootstrap samples
        seed: Random seed for reproducibility

    Returns:
        Array of shape (n_bootstrap, len(data))
    """
```

**Question:** How should the forward volatility target be defined at horizon=1?

**Problem:** The current definition `target_t(horizon) = std(r_{t+1}, ..., r_{t+horizon})` is undefined at `horizon=1`: sample std with one observation is `NaN`, population std is `0`. Neither is meaningful.

**Candidate resolution (not selected):** Use `RV_{t,h} = Σ_{i=1}^{h} r_{t+i}²` and `σ_{t,h} = sqrt(RV_{t,h})`, which reduces to `σ_{t,1} = |r_{t+1}|` at horizon=1.

### 10. HAR Component Window Semantics

**Status:** OPEN — DEFERRED TO STAGE 3

**Question:** Are HAR model component windows (6, 30, 90 bars) literal daily/weekly/monthly periods, or implementation-inherited parameters?

**Problem:** 90 bars = 15 trading days, not one trading month (~22 trading days ≈ 132 bars). The names "daily/weekly/monthly" may be misleading.

**Options:**
- (a) Keep 6/30/90 as canonical parameters with non-calendar labels
- (b) Redefine to 6/30/132 for genuine daily/weekly/monthly semantics

**Impact:** Affects HAR model interpretation and comparison with literature. Must be resolved in Stage 3.

### 11. Regime-Label Methodology (Fold-Relative vs. Global)

**Status:** OPEN — DEFERRED TO STAGE 3

**Question:** Should regime labels be fold-relative (thresholds recomputed per fold) or globally predeclared (fixed from a reference period)?

**Options:**
- **Fold-relative:** Each fold computes its own `q33`/`q67` thresholds. Causally safe, but labels not comparable across folds.
- **Globally predeclared:** Thresholds fixed once. Comparable, but requires justification that the reference period doesn't leak information.

**Impact:** Affects "2/3 of predefined regimes" robustness target and "regime consistency" metric. Must be resolved before Stage 7.
