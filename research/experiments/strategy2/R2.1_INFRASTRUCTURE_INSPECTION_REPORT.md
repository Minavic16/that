- A provenance record (source, timestamp, commit hash)
- A hash/checksum for integrity verification

## 9. Causality-Control Design

**Current implementation** (`causality_tests.py`): 10 invariants testing that modifying future data does not change past forecasts. This is the synthetic perturbation approach required by the ROS.

**Required additions:**

1. **Perturbation framework:** Formalize the existing pattern into a reusable `causality.perturb_and_verify()` function that:
   - Takes a function `f(data) → result`
   - Perturbs `data[t+n:]` for increasing `n`
   - Verifies `f(data[:t])` is unchanged
   - Returns pass/fail with diagnostic

2. **Normalization causality:** Test that feature normalization (e.g., z-score scaling) uses only training data statistics, not future data.

3. **Hyperparameter causality:** Test that any hyperparameter selection (window sizes, spans) does not inspect OOS results.

4. **Regime label causality:** If regime labels are used, test that they do not contain future information.

## 10. Validation-Engine Design

**Two distinct frameworks required by ROS §11:**

**Partition A — Causal Walk-Forward (Deployment-Relevant OOS):**
- Sequential training windows
- Each OOS block uses only data after the training window
- No future data leaks into earlier blocks
- This is what `walk_forward_evaluate()` currently implements

**Partition B — Blocked Temporal Generalization (Diagnostic Only):**
- Alternating IS/OOS blocks
- Every block gets evaluated in both IS and OOS roles
- Must be labeled "TEMPORAL GENERALIZATION DIAGNOSTIC" — never "OOS"
- Purpose: determine if effect is localized to a historical segment

**Key design rule:** Partition A results are deployment-relevant. Partition B results are diagnostic only. Never conflate them.

## 14. Critical-Infrastructure Change-Control Design

**Required gate per ROS §27:**

```
CHANGE PROPOSED → SPECIFICATION → IMPACT ASSESSMENT → IMPLEMENTATION →
UNIT TESTS → CAUSALITY/REGRESSION TESTS → CONTROLLED VALIDATION →
COMMIT → RESEARCH CONTINUES
```

**Hard rules:**
1. Every research-critical change must follow this pipeline
2. If a change can alter previous conclusions, previous results must be explicitly classified as "potentially affected"
3. Historical results must not be silently overwritten
4. Production isolation: research changes never modify production code

## 19. Conflicts or Ambiguities Requiring Human Approval

### 1. `RESEARCH_OPERATING_SYSTEM.md` not on `research/strategy-2` branch

The governance doc exists on `origin/master` (commit `cae0428`) but is not on the `research/strategy-2` branch. The R2.1 experiment was designed against this doc but the doc was not present during development. **Decision needed:** Should the ROS be cherry-picked/merged into `research/strategy-2` before proceeding?

### 2. Existing bootstrap code in `research/shared/` vs. building new

There are 15+ bootstrap implementations scattered across `research/experiments/`. The ROS requires block bootstrap methods specifically. **Decision needed:** Should we (a) build new block bootstrap from scratch in `research/apparatus/statistics/`, (b) adapt existing implementations from `research/shared/`, or (c) use an external library?

### 3. Research ledger location and format

ROS §24 specifies 35+ fields but does not specify storage format or location. **Decision needed:** Should the ledger be (a) one JSON file per experiment in `research/ledger/`, (b) a single SQLite database, or (c) a CSV/parquet file?

### 4. Multiple testing correction method

ROS §16 requires distinguishing confirmatory vs exploratory tests and specifying multiple comparison correction, but does not specify which method. **Decision needed:** Which correction method should be pre-registered? (Bonferroni, BH-FDR, Holm, or other?)

### 5. Block size selection for temporal robustness

ROS §12 says "Block size must not become an optimization variable" and lists weekly/monthly/quarterly/semiannual/annual. But with ~15 years of 4H data, some block sizes may be too small for reliable estimation. **Decision needed:** Should block sizes be fixed at specific values (e.g., 6 months, 1 year, 2 years) or adaptive to data length?

### 6. Economic metrics scope

ROS §18 and Tier 4 metrics list Sharpe, Sortino, drawdown, turnover, exposure, tail loss, transaction costs. But R2.1 is a volatility forecasting experiment, not a trading strategy. **Decision needed:** Are economic metrics required for R2.1, or only if R2.1 maps to a trading function (NQTS Gate 8/9)?

### 7. Experiment versioning scheme

ROS §25 requires "new experiment/version identifier" for methodological corrections. But no versioning scheme is defined. **Decision needed:** Should experiment versions follow semver (R2.1.0, R2.1.1), date-based (R2.1-20260916), or commit-based (R2.1-cd71556)?
