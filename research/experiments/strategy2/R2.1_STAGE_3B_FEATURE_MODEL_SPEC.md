## 1. Backward-Looking Features

### 1.1 Feature Catalog

Every feature available to models at forecast time `t` is a function of observations at times `≤ t` only.

| Feature | Formula | Lookback | NaN head | Purpose |
|---|---|---|---|---|
| Log return | `r_t = log(close_t / close_{t-1})` | 1 bar | 1 | Base signal for all models |
| Squared return | `r_t²` | 1 bar | 1 | Variance proxy, HAR regressand |
| Backward realized variance | `RV_var(t, w) = Σ_{i=0}^{w-1} r_{t-i}²` | w bars | w | Cumulative variance over window |
| Backward realized volatility | `RV(t, w) = sqrt(RV_var(t, w))` | w bars | w | Volatility feature for HAR |
| Rolling standard deviation | `σ(t, w) = std(r_{t-w+1}, ..., r_t)` | w bars | w | Baseline model input |
| EWMA variance | `σ²_ewma(t, span) = EWMA(r², span)` | span bars | 1 | Exponentially weighted vol |
| Parkinson volatility | `P(t, w) = sqrt(mean(ln(H/L)²) / (4·ln(2)))` | w bars | w | Range-based volatility (optional) |

### 1.2 Causality Invariant

For every feature `f_t`:

```
f_t = f(X_{≤ t})
```

No feature at time `t` may use any observation from time `> t`. This is enforced by:
1. All rolling computations use `.shift(0)` or `.shift(negative)` — never `.shift(positive)` for backward features
2. Perturbation tests (§7) verify this invariant empirically

### 1.3 Gap Handling

- Missing bars are preserved as gaps in the DatetimeIndex — they are NOT imputed, forward-filled, or interpolated.
- Rolling computations skip gaps: `.rolling(window=w, min_periods=w)` naturally produces NaN at gap boundaries.
- Models must handle NaN inputs gracefully (§9).
- Gap-aware models may optionally accept a gap mask, but this is not required for Stage 3B.

### 1.4 NaN Head Convention

For a feature with lookback `w`:
- The first `w - 1` observations produce NaN (insufficient history)
- The first return (`r_0`) is NaN by definition
- Therefore a feature with lookback `w` has `max(w - 1, 1)` leading NaN values

### 1.5 Timestamp Alignment

- All features share the same DatetimeIndex as the input close prices
- Feature at index `t` uses only data from indices `≤ t`
- No resampling, no interpolation, no alignment tricks

### 1.6 Implementation Location

```
apparatus/features/returns.py       — compute_log_returns (Stage 3A, unchanged)
apparatus/features/volatility.py    — realized_volatility_backward (Stage 3A, extend)
apparatus/features/indicators.py    — NEW: rolling features, Parkinson, EWMA
```

## 2. Model Interfaces

### 2.1 VolatilityModel Protocol

All six models implement this interface:

```python
from typing import Protocol
import pandas as pd
import numpy as np

class VolatilityModel(Protocol):
    """Protocol for all R2.1 volatility models.

    All models forecast REALIZED VOLATILITY (not variance).
    The output of forecast() is σ̂ — a non-negative float.
    """

    @property
    def name(self) -> str:
        """Unique model identifier (e.g., 'GARCH(1,1)', 'HAR-RV')."""
        ...

    @property
    def min_observations(self) -> int:
        """Minimum observations required for fitting/forecasting."""
        ...

    def fit(self, returns: pd.Series) -> ModelDiagnostics:
        """Fit model on historical returns.

        CAUSAL: uses only the provided returns. No future information.
        Must handle: empty series, series with NaN, series < minimum length.

        Returns: ModelDiagnostics with convergence status.
        """
        ...

    def forecast(self) -> float:
        """Generate 1-step-ahead volatility forecast.

        CAUSAL: uses only fitted state from last fit() call.
        Returns: non-negative float (realized volatility estimate).
        NaN if model failed to fit or converge.
        """
        ...
```

### 2.2 Forecast Semantics — Critical Consistency Rule

**Every model forecasts realized volatility σ̂, not variance σ̂².**

This means:
- GARCH models internally estimate variance, but `forecast()` returns `sqrt(variance)` after any necessary scaling reversal
- HAR-RV internally regresses on realized variance (squared returns), but `forecast()` returns `sqrt(prediction)`
- Naive, RollingVol, EWMA already output volatility directly

The target variable is `RV(t, h) = sqrt(Σ r²)` (realized volatility), so forecast and target are in the same units. No downstream transformation is needed.

### 2.3 Per-Model Specification

#### NaiveModel (Persistence)

| Property | Value |
|---|---|
| Mathematical definition | σ̂_{t+1} = \|r_t\| |
| Required inputs | Last observed return |
| Output semantics | Absolute last return (= realized vol at h=1) |
| Fitting data | Last observation only |
| Forecast horizon handling | Always 1-step; identical for all horizons |
| Minimum observations | 1 |
| Convergence | Always converges |
| Configuration | None |
| Diagnostics | `last_return`, `last_abs_return` |

**Forecast formula:** `forecast() = |r_t|` where `r_t` is the last observed return.

#### RollingVolModel

| Property | Value |
|---|---|
| Mathematical definition | σ̂_{t+1} = std(r_{t-W+1}, ..., r_t) |
| Required inputs | Last W returns |
| Output semantics | Sample standard deviation over window |
| Fitting data | Last W returns |
| Forecast horizon handling | Always 1-step; identical for all horizons |
| Minimum observations | W (window size) |
| Convergence | Always converges if ≥ W observations |
| Configuration | `window: int` (default 24) |
| Diagnostics | `window`, `n_obs_used`, `std_value` |

**Forecast formula:** `forecast() = returns[-window:].std()`

#### EWMAModel

| Property | Value |
|---|---|
| Mathematical definition | σ̂_{t+1} = sqrt(EWMA(r², span)) |
| Required inputs | All returns (exponential weighting) |
| Output semantics | Exponentially weighted standard deviation |
| Fitting data | All available returns |
| Forecast horizon handling | Always 1-step; identical for all horizons |
| Minimum observations | 2 |
| Convergence | Always converges if ≥ 2 observations |
| Configuration | `span: int` (default 24) |
| Diagnostics | `span`, `n_obs`, `ewm_variance` |

**Forecast formula:** `forecast() = sqrt(returns.ewm(span=span).var().iloc[-1])`

#### GARCHModel — GARCH(1,1)

| Property | Value |
|---|---|
| Mathematical definition | σ²_t = ω + α·ε²_{t-1} + β·σ²_{t-1} |
| Required inputs | Return series (≥ 30 observations) |
| Output semantics | `sqrt(variance_forecast)` — volatility, not variance |
| Fitting data | Full training series, scaled ×100 for numerical stability |
| Forecast horizon handling | 1-step-ahead only (arch library) |
| Minimum observations | 30 |
| Convergence | May fail; fallback to rolling std |
| Configuration | `mean: str = "Constant"`, `vol: str = "GARCH"`, `p: int = 1`, `q: int = 1` |
| Diagnostics | `converged`, `n_obs`, `parameters: dict`, `log_likelihood`, `aic`, `bic`, `warning` |

**Critical scaling note:** Returns are multiplied by 100 before fitting (arch library convention). The variance forecast is divided by 100² before returning `sqrt()`:

```python
scaled = returns * 100
am = arch_model(scaled, ...)
fitted = am.fit(...)
var_forecast = fitted.forecast(horizon=1).variance.iloc[-1].values[0]
volatility = np.sqrt(var_forecast) / 100  # reverse the ×100 scaling
```

**Failure behavior:** If fitting fails or `n_obs < 30`, returns `NaN` and sets `converged=False`. Does NOT silently fall back to rolling std (that was Phase 1 behavior, corrected here).

#### GJRGARCHModel — GJR-GARCH(1,1)

| Property | Value |
|---|---|
| Mathematical definition | σ²_t = ω + (α + γ·I_{t-1})·ε²_{t-1} + β·σ²_{t-1} |
| Required inputs | Return series (≥ 30 observations) |
| Output semantics | `sqrt(variance_forecast)` — volatility, not variance |
| Fitting data | Full training series, scaled ×100 |
| Forecast horizon handling | 1-step-ahead only |
| Minimum observations | 30 |
| Convergence | May fail; returns NaN |
| Configuration | Fixed: `mean="Constant"`, `vol="GARCH"`, `p=1`, `o=1`, `q=1` |
| Diagnostics | Same as GARCH + `gamma` (asymmetry parameter) |

**Scaling:** Same as GARCH. Returns ×100, variance forecast /100², then `sqrt()`.

#### HARModel — HAR-RV

| Property | Value |
|---|---|
| Mathematical definition | RV̂_{t+1} = c + β_d·RV_d(t) + β_w·RV_w(t) + β_m·RV_m(t) |
| Required inputs | Squared returns (≥ monthly + 10 = 142 observations) |
| Output semantics | `sqrt(prediction)` — volatility, not variance |
| Fitting data | Squared returns, OLS regression |
| Forecast horizon handling | 1-step-ahead (regress on current features, predict next) |
| Minimum observations | 142 (monthly window + OLS overhead) |
| Convergence | OLS always solves if sufficient data; may produce poor fits |
| Configuration | `daily: int = 6`, `weekly: int = 30`, `monthly: int = 132` |
| Diagnostics | `coefficients`, `n_obs`, `r_squared`, `condition_number` |

**Critical definition (approved in Stage 2):**
- `daily = 6` bars (≈ 1 trading day at 4H)
- `weekly = 30` bars (≈ 5 trading days)
- `monthly = 132` bars (≈ 22 trading days)

**Regressors are realized variance (squared returns), NOT realized volatility:**
- `RV_d(t) = mean(r²_{t-5:t})` — average squared return over daily window
- `RV_w(t) = mean(r²_{t-29:t})` — average squared return over weekly window
- `RV_m(t) = mean(r²_{t-131:t})` — average squared return over monthly window

**Target is realized variance:** `y_t = r²_{t+1}` (next period's squared return)

**Forecast transformation:** `forecast() = sqrt(max(预测_variance, 0))`

This ensures HAR-RV outputs realized volatility, consistent with all other models.

## 3. HAR-RV Definition (Detailed)

### 3.1 Dependent Variable

```
y_t = r²_{t+1}
```

The dependent variable is the **next period's realized variance** (squared log return).

### 3.2 Regressors

| Regressor | Formula | Window | Interpretation |
|---|---|---|---|
| RV_d(t) | `mean(r²_{t-5:t})` | 6 bars | Daily realized variance |
| RV_w(t) | `mean(r²_{t-29:t})` | 30 bars | Weekly realized variance |
| RV_m(t) | `mean(r²_{t-131:t})` | 132 bars | Monthly realized variance |

All regressors are **realized variance** (mean of squared returns), not realized volatility.

### 3.3 Regression

```
y_t = c + β_d · RV_d(t) + β_w · RV_w(t) + β_m · RV_m(t) + ε_t
```

Fitted via OLS: `β = (X'X)^{-1} X'y`

### 3.4 Forecast

```python
# At forecast time t, build features from returns up to t
X_new = [RV_d(t), RV_w(t), RV_m(t)]
predicted_variance = intercept + coefficients @ X_new
forecast_volatility = sqrt(max(predicted_variance, 0))
```

### 3.5 Minimum Observations

- Monthly window: 132 bars
- OLS overhead: ≥ 3 regressors + 1 intercept
- Minimum total: 132 + 10 = 142 bars (matching §E4 of Stage 2 spec)

### 3.6 Horizon Handling

HAR-RV is inherently a 1-step-ahead model. For multi-step forecasting, two approaches exist:
1. **Iterated:** Forecast r²_{t+1}, then use it as an input to forecast r²_{t+2} (introduces accumulating error)
2. **Direct:** Train separate models for each horizon (not implemented in Stage 3B)

Stage 3B implements the 1-step-ahead forecast only. The evaluation engine (Stage 3C) will handle multi-step comparison by evaluating the 1-step forecast against each horizon's target.

## 5. Walk-Forward Compatibility

### 5.1 How Models Receive Data

The walk-forward engine (Stage 3C) will call each model as follows:

```
For each fold t in [train_window, n - horizon, step]:
    1. Slice returns[0:t] as training data
    2. Call model.fit(returns[0:t])
    3. Call model.forecast() → σ̂
    4. Compare σ̂ to RV(t, horizon) computed from returns[t+1:t+horizon+1]
```

### 5.2 Leakage Boundaries

| Boundary | Rule |
|---|---|
| Training data | `returns[0:t]` — strictly before forecast origin |
| Forecast origin | Timestamp `t` — the last bar used for fitting |
| Target window | `returns[t+1 : t+horizon+1]` — strictly after forecast origin |
| Feature computation | All features at time `t` use only `returns[0:t+1]` |
| Model state | After `fit()`, model state encodes only training data |

### 5.3 Model State After Fit

After `fit(returns)`, the model must be in a state where `forecast()` returns the 1-step-ahead forecast using only the fitted state. No additional data is passed to `forecast()`.

This design means:
- The model "remembers" the training data through its fitted parameters
- `forecast()` is a pure function of the fitted state
- No data leakage is possible through the forecast call

## 9. Failure Behavior

### 9.1 Failure Modes and Responses

| Failure Mode | Model Response | Diagnostics | Forecast |
|---|---|---|---|
| Insufficient observations (`n < min_obs`) | Refuse to fit | `converged=False`, `warning="insufficient_data"` | `NaN` |
| All returns are zero | Fit succeeds (trivial) | `converged=True` | `0.0` |
| GARCH non-convergence | Refuse to fit | `converged=False`, `warning=arch_message` | `NaN` |
| GARCH numerical instability | Refuse to fit | `converged=False`, `warning="numerical_instability"` | `NaN` |
| OLS singular matrix (HAR) | Refuse to fit | `converged=False`, `warning="singular_matrix"` | `NaN` |
| Invalid input (NaN in critical position) | Skip NaN positions | `converged=True` (if enough clean data) | computed |
| Empty series | Refuse to fit | `converged=False`, `warning="empty_series"` | `NaN` |

### 9.2 Rules

1. **Never silently fall back.** If a model cannot fit, `forecast()` returns `NaN`, not a degraded approximation.
2. **Never suppress warnings.** All convergence warnings are captured in diagnostics.
3. **Never return negative volatility.** `forecast()` returns `max(sqrt(prediction), 0.0)` or `NaN`.
4. **Never impute missing data.** If the input series has gaps, the model receives the gapped series.

## 12. Market Simulator — Architectural Capture

**This section is documentation only. No implementation.**

### 12.1 Position in System Architecture

The Market Simulator is a peer core engine, not a sub-component of R2.1:

```
Research Operating System
        │
        ├── Historical Data Engine
        ├── Feature / Target Engine     ← Stage 3A/3B builds this
        ├── Model Engine                ← Stage 3B builds this
        ├── Validation Engine           ← Stage 3C builds this
        ├── Statistical / Monte Carlo Engine
        ├── Market Simulator            ← future core layer, captured here
        ├── Backtest Engine
        ├── Portfolio / Risk Engine
        └── Research Ledger
```

### 12.2 Two Required Modes

1. **Historical reconstruction** — uses observed spread, prices, timestamps, available liquidity proxies, known commissions, documented execution assumptions. Answers: "what would have happened under these specified historical conditions?"

2. **Stochastic market simulation** — randomizes predeclared environmental parameters (spread, slippage, latency, execution delay, fill probability, volatility perturbations, gap behavior, liquidity conditions, execution noise). Answers: "does the strategy remain viable when the market/execution environment is perturbed?"

### 12.3 Conceptual Flow

**Strategy-facing view:**
```
Strategy → standardized Strategy API → Market Simulator/Environment
→ Execution Simulator → Portfolio/Account → Backtest/Research Metrics + Ledger
```

**Environment-stack view:**
```
Historical Data → Market Environment (spread, liquidity, volatility, gaps,
session, latency, slippage, commission, execution rules)
→ Strategy API → Execution Simulator (orders, fills, partial fills,
rejection, latency, slippage)
→ Portfolio/Account (equity, margin, drawdown, exposure, P&L)
→ Backtest/Research Metrics + Ledger
```

### 12.4 Critical Rule

The simulator must never become a mechanism for making a bad strategy look good. Every stochastic parameter must eventually be specified with: source; empirical basis; distribution; bounds; seed; correlation assumptions; reason for inclusion; and which mode it belongs to.

Spread perturbation must derive from an observed historical distribution → a fitted distribution or empirical sampling → a predeclared perturbation range — never "increase spread randomly until the strategy survives."

### 12.5 Interfaces to Capture Now

Stage 3B's model interface is designed with this future consumer in mind:
