## 0. Scope

Stage 3B implements the feature construction layer and all six volatility models required by the approved R2.1 experiment. It does NOT implement the walk-forward evaluation engine, the blocked temporal generalization framework, the metric engine, the bootstrap/MC engine, or the research ledger. Those are Stage 3C+ deliverables.

Stage 3B establishes the contract between "what the data pipeline produces" and "what the evaluation engine will consume." The evaluation engine is not built yet, but the model interface must be shaped so it can be consumed without modification.

### 0.1 Canonical Implementation Boundary

`apparatus/` is the canonical Stage 3B implementation. The legacy Phase 1 module (`volatility_models.py` and related files at `research/experiments/strategy2/`) is frozen legacy code, not to be imported into new research work. Known divergences:

| Item | Phase 1 (`volatility_models.py`) | Stage 3B (`apparatus/`) |

## 1. Backward-Looking Features

### 1.1 Feature Catalog

Every feature available to models at forecast time `t` is a function of observations at times `≤ t` only.

| Feature | Formula | Lookback | NaN head | Purpose |
|---|---|---|---|---|
| Log return | `r_t = log(close_t / close_{t-1})` | 1 bar | 1 | Base signal for all models |
| Squared return | `r_t²` | 1 bar | 1 | Variance proxy, HAR regressand |
| Backward realized variance | `RV_var(t, w) = Σ_{i=0}^{w-1} r_{t-i}²` | w bars | w | Cumulative variance over window |
| Backward realized volatility | `RV(t, w) = sqrt(RV_var(t, w))` | w bars | w | Volatility feature for HAR |
| Rolling standard deviation | `σ(t, w) = std(r_{t-w+1}, ..., r_t)` | w bars | w | Baseline model input |
| EWMA variance | `σ²_ewma(t, span) = EWMA(r², span)` | span bars | 1 | Exponentially weighted vol |
| Parkinson volatility | `P(t, w) = sqrt(mean(ln(H/L)²) / (4·ln(2)))` | w bars | w | Range-based volatility (optional) |

### 1.2 Causality Invariant

For every feature `f_t`:

```
f_t = f(X_{≤ t})
```

No feature at time `t` may use any observation from time `> t`. This is enforced by:
1. All rolling computations use `.shift(0)` or `.shift(negative)` — never `.shift(positive)` for backward features
2. Perturbation tests (§7) verify this invariant empirically

### 1.3 Gap Handling

- Missing bars are preserved as gaps in the DatetimeIndex — they are NOT imputed, forward-filled, or interpolated.
- Models must handle NaN inputs gracefully (§9).
- Gap-aware models may optionally accept a gap mask, but this is not required for Stage 3B.
- **Rolling window caveat:** `.rolling(window=w, min_periods=w)` is observation-count based, not market-time aware. A window can span a weekend gap without signal. This is addressed at the model level in §9 (Gap Semantics).

### 1.4 NaN Head Convention

For a feature with lookback `w`:
- The first `w - 1` observations produce NaN (insufficient history)
- The first return (`r_0`) is NaN by definition
- Therefore a feature with lookback `w` has `max(w - 1, 1)` leading NaN values

### 1.5 Timestamp Alignment

- All features share the same DatetimeIndex as the input close prices
- Feature at index `t` uses only data from indices `≤ t`
- No resampling, no interpolation, no alignment tricks

### 1.6 Implementation Location

```
apparatus/features/returns.py       — compute_log_returns (Stage 3A, unchanged)
apparatus/features/volatility.py    — realized_volatility_backward (Stage 3A, extend)
apparatus/features/indicators.py    — NEW: rolling features, Parkinson, EWMA
```

## 2. Model Interfaces

### 2.1 VolatilityModel Protocol

All six models implement this interface:

```python
from typing import Protocol
import pandas as pd
import numpy as np

class VolatilityModel(Protocol):
    """Protocol for all R2.1 volatility models.

    All models produce forecasts tagged with a horizon.
    The forecast() method accepts a horizon parameter and returns
    a ForecastResult containing the volatility estimate and metadata.
    """

    @property
    def name(self) -> str:
        """Unique model identifier (e.g., 'GARCH(1,1)', 'HAR-RV-h6')."""
        ...

    @property
    def min_observations(self) -> int:
        """Minimum observations required for fitting/forecasting."""
        ...

    def fit(self, returns: pd.Series, gaps: pd.Series | None = None) -> ModelDiagnostics:
        """Fit model on historical returns.

        CAUSAL: uses only the provided returns. No future information.
        Must handle: empty series, series with NaN, series < minimum length.

        Args:
            returns: Historical log returns.
            gaps: Optional boolean series marking gap boundaries (True = gap).
                  If provided, state-dependent models must not propagate
                  state across gap boundaries.

        Returns: ModelDiagnostics with convergence status.
        """
        ...

    def forecast(self, horizon: int) -> ForecastResult:
        """Generate volatility forecast for the specified horizon.

        CAUSAL: uses only fitted state from last fit() call.

        Args:
            horizon: Forecast horizon in bars (1, 3, 6, or 12).

        Returns: ForecastResult with volatility estimate, horizon tag,
                 and validity flag. Invalid if model failed to fit,
                 horizon is unsupported, or stationarity gate blocks.
        """
        ...
```

### 2.2 ForecastResult Structure

```python
@dataclass
class ForecastResult:
    """Horizon-tagged forecast result."""

    volatility: float          # Realized volatility estimate (non-negative)
    horizon: int               # Forecast horizon in bars
    valid: bool                # False if forecast cannot be produced
    diagnostic: str | None     # e.g., "FORECAST_UNAVAILABLE", "STATIONARITY_VIOLATION"
    model_name: str            # Model identifier

    def __post_init__(self):
        if self.valid and self.volatility < 0:
            raise ValueError(f"Forecast volatility must be >= 0, got {self.volatility}")
```

### 2.3 Forecast-Horizon / Target-Horizon Consistency Invariant

**Contract rule:** A forecast declared for horizon `h` may only be evaluated against a target defined for the same `h`, unless a methodology explicitly defines a valid transformation between them (which the per-model resolutions in §2.4 provide).

Every `forecast()` call returns metadata tagging its horizon explicitly. Evaluation code must assert `forecast.horizon == target.horizon` before scoring, and must raise/flag a structured error (not a silent numeric comparison) on mismatch.

### 2.4 Multi-Horizon Forecast Semantics (Per Model Class)

Each model class has a predeclared method for producing forecasts at horizons `h ∈ {1, 3, 6, 12}`. These are methodological choices grounded in standard practice — not chosen for expected performance.

#### Naive, RollingVol, EWMA — Square-Root-of-Time Scaling

None of these models have mean-reverting dynamics. The standard treatment (RiskMetrics convention) applies:

```
RV̂(t, h) = σ̂_t × sqrt(h)
```

where `σ̂_t` is each model's existing 1-step volatility estimate.

**Explicit assumption:** This assumes flat volatility over the horizon (no mean reversion). This is the assumption being made, not a hidden approximation. It is what makes the transformation valid for all three models without redesigning them.

#### GARCH(1,1), GJR-GARCH(1,1) — Analytical Multi-Step Variance Aggregation

For k ≥ 2, use the standard GARCH term-structure recursion:

```
σ²_{t+k} = ω + (α+β) × σ²_{t+k-1}
RV̂(t, h) = sqrt( sum_{i=1}^{h} σ²_{t+i} )
```

**Mandatory stationarity gate:** If `α + β >= 1`, the multi-step forecast for h > 1 is invalid. The model must report `FORECAST_UNAVAILABLE` with diagnostic `"STATIONARITY_VIOLATION"` for that fold/horizon — not a silently extrapolated (and diverging) value.

This check is part of the diagnostics structure (§6). It applies per-fold: a model that is stationary in one fold but non-stationary in another correctly reports `FORECAST_UNAVAILABLE` only for the non-stationary fold.

**GJR-GARCH-specific sub-issue (OPEN — requires explicit sign-off):**

The leverage term's multi-step expectation requires an assumption about `E[I(ε_{t+i}<0)]`, the probability the innovation is negative at each future step. The conventional simplification approximates this as `0.5` (unconditional/symmetric-distribution assumption). This is usable now since the Monte Carlo engine that could simulate this properly doesn't exist yet (correctly out of scope for Stage 3B per the statistical/MC boundary).

**This approximation is NOT adopted as a silent default.** It is flagged here as an open decision requiring explicit approval. Implementation of the GJR multi-step term must wait for this specific approval even if everything else in this correction pass is accepted.

Until approved, GJR-GARCH multi-step forecasts for h > 1 report `FORECAST_UNAVAILABLE` with diagnostic `"GJR_ASYMMETRY_NOT_APPROVED"`.

#### HAR-RV — Direct Per-Horizon Regression (Corsi-Style)

For h ∈ {1, 3, 6, 12}, fit a **separate HAR regression per horizon**. The regressors (`RV_d(t)`, `RV_w(t)`, `RV_m(t)`) do not change across horizons — only the dependent variable and the fitted coefficients change, one regression per h.

```
RV(t, h) = c_h + β_d,h · RV_d(t) + β_w,h · RV_w(t) + β_m,h · RV_m(t) + ε_t,h
```

where `RV(t, h) = sqrt(Σ_{i=1}^{h} r²_{t+i})` is the realized-volatility target for horizon `h`.

This means four HAR model instances per pair (one per canonical horizon), not one model reused four ways. This is the standard direct-horizon HAR-RV practice — it sidesteps the aggregation problem entirely by reusing the Stage 3A target definition as-is.

At h=1, the target degenerates to `|r_{t+1}|` (consistent with §C10 of the Stage 2 spec).

## 3. HAR-RV Definition (Detailed)

### 3.1 Regressors (Approved)

HAR regressors are `mean(r²)` over the daily(6)/weekly(30)/monthly(132) windows, computed causally from data `≤ t` only. This is explicitly approved as part of the R2.1 model definition.

| Regressor | Formula | Window | Interpretation |
|---|---|---|---|
| RV_d(t) | `mean(r²_{t-5:t})` | 6 bars | Daily realized variance |
| RV_w(t) | `mean(r²_{t-29:t})` | 30 bars | Weekly realized variance |
| RV_m(t) | `mean(r²_{t-131:t})` | 132 bars | Monthly realized variance |

### 3.2 Dependent Variable (Per-Horizon)

For each horizon `h`, the dependent variable is the realized-volatility target:

```
RV(t, h) = sqrt( Σ_{i=1}^{h} r²_{t+i} )
```

This is the same definition as the Stage 3A forward target (§C10/F4 of Stage 2 spec). The h=1 case degenerates to `|r_{t+1}|`.

### 3.3 Regression (Per-Horizon)

For each horizon `h ∈ {1, 3, 6, 12}`:

```
RV(t, h) = c_h + β_d,h · RV_d(t) + β_w,h · RV_w(t) + β_m,h · RV_m(t) + ε_t,h
```

Fitted via OLS: `β_h = (X'X)^{-1} X'y_h`

Each horizon produces its own set of coefficients. Changing the h=12 target data must not alter the h=1, h=3, or h=6 fitted coefficients.

### 3.4 Forecast

```python
# At forecast time t, build features from returns up to t
X_new = [RV_d(t), RV_w(t), RV_m(t)]

# For each horizon h, use the horizon-specific coefficients
predicted_volatility_h = c_h + coefficients_h @ X_new
forecast_result = ForecastResult(
    volatility=max(predicted_volatility_h, 0.0),
    horizon=h,
    valid=True,
    diagnostic=None,
    model_name=f"HAR-RV-h{h}"
)
```

### 3.5 Minimum Observations

- Monthly window: 132 bars
- OLS overhead: ≥ 3 regressors + 1 intercept
- Minimum total: 132 + 10 = 142 bars (matching §E4 of Stage 2 spec)
- Each horizon is fit independently; the minimum applies to each

### 3.6 Per-Horizon Independence

Four HAR model instances are created per pair, one per horizon. They are fit independently. The h=12 model uses a different dependent variable than the h=1 model, but the same regressors. Changing the training window's tail (which affects the h=12 target for the most recent folds) must not change the h=1 fitted coefficients, because they are separate OLS regressions.

## 5. Walk-Forward Compatibility

### 5.1 How Models Receive Data

The walk-forward engine (Stage 3C) will call each model as follows:

```
For each fold t in [train_window, n - max(horizon), step]:
    1. Slice returns[0:t] as training data
    2. Call model.fit(returns[0:t], gaps=gaps[0:t])
    3. For each horizon h in horizons:
       a. Call model.forecast(horizon=h) → ForecastResult
       b. Assert forecast.horizon == h
       c. Compare forecast.volatility to RV(t, h) computed from returns[t+1:t+h+1]
```

### 5.2 Leakage Boundaries

| Boundary | Rule |
|---|---|
| Training data | `returns[0:t]` — strictly before forecast origin |
| Forecast origin | Timestamp `t` — the last bar used for fitting |
| Target window | `returns[t+1 : t+h+1]` — strictly after forecast origin |
| Feature computation | All features at time `t` use only `returns[0:t+1]` |
| Model state | After `fit()`, model state encodes only training data |

### 5.3 Model State After Fit

After `fit(returns)`, the model must be in a state where `forecast(horizon=h)` returns the horizon-appropriate forecast using only the fitted state. No additional data is passed to `forecast()`.

This design means:
- The model "remembers" the training data through its fitted parameters
- `forecast()` is a pure function of the fitted state
- No data leakage is possible through the forecast call

## 6. Model Diagnostics

### 6.1 Diagnostics Structure

```python
@dataclass
class ModelDiagnostics:
    """Standard diagnostics for all models."""

    # Convergence
    converged: bool
    warning: str | None

    # Observations
    n_observations: int
    min_observations_required: int

    # Parameters (model-specific)
    parameters: dict[str, float]

    # Fit quality (where applicable)
    log_likelihood: float | None
    aic: float | None
    bic: float | None

    # GARCH-specific: stationarity gate
    alpha_plus_beta: float | None  # GARCH/GJR-GARCH only
    stationary: bool | None        # True if α+β < 1, None for non-GARCH models

    # HAR-specific: per-horizon coefficients
    horizons_fitted: list[int] | None  # HAR only: [1, 3, 6, 12]
    coefficients_per_horizon: dict[int, np.ndarray] | None  # HAR only

    # Metadata
    model_name: str
    fit_timestamp: pd.Timestamp | None
```

### 6.2 Per-Model Diagnostics

| Model | Parameters | log_likelihood | aic/bic | Extra |
|---|---|---|---|---|
| Naive | `{"last_return": r_t}` | None | None | — |
| RollingVol | `{"window": W, "std": σ}` | None | None | — |
| EWMA | `{"span": S, "ewm_var": σ²}` | None | None | — |
| GARCH | `{ω, α, β}` | ✓ | ✓ | `alpha_plus_beta`, `stationary` |
| GJR-GARCH | `{ω, α, β, γ}` | ✓ | ✓ | `alpha_plus_beta`, `stationary` |
| HAR-RV | `{c_h, β_d,h, β_w,h, β_m,h}` per h | None | None | `horizons_fitted`, `coefficients_per_horizon` |

### 6.3 Diagnostic Rules

1. Diagnostics are produced by `fit()` and stored on the model instance
2. Diagnostics must NOT alter the forecast silently
3. If `converged=False`, `forecast()` must return `valid=False` with `NaN` volatility
4. If `stationary=False` (GARCH/GJR-GARCH), multi-step forecasts (h > 1) must return `valid=False` with diagnostic `"STATIONARITY_VIOLATION"`
5. Diagnostics are recorded in the ledger (Stage 3C) but do not affect the evaluation engine

## 9. Failure Behavior

### 9.1 Failure Modes and Responses

| Failure Mode | Model Response | Diagnostics | Forecast |
|---|---|---|---|
| Insufficient observations (`n < min_obs`) | Refuse to fit | `converged=False`, `warning="insufficient_data"` | `valid=False` |
| All returns are zero | Fit succeeds (trivial) | `converged=True` | `valid=True`, `volatility=0.0` |
| GARCH non-convergence | Refuse to fit | `converged=False`, `warning=arch_message` | `valid=False` |
| GARCH numerical instability | Refuse to fit | `converged=False`, `warning="numerical_instability"` | `valid=False` |
| GARCH non-stationary (`α+β >= 1`) | Fit succeeds, but multi-step blocked | `stationary=False` | h=1: `valid=True`; h>1: `valid=False`, `"STATIONARITY_VIOLATION"` |
| OLS singular matrix (HAR) | Refuse to fit | `converged=False`, `warning="singular_matrix"` | `valid=False` |
| HAR horizon not fitted | N/A | `horizons_fitted` excludes h | h: `valid=False`, `"HAR_HORIZON_NOT_FITTED"` |
| Invalid input (NaN in critical position) | Skip NaN positions | `converged=True` (if enough clean data) | computed |
| Empty series | Refuse to fit | `converged=False`, `warning="empty_series"` | `valid=False` |
| Forecast horizon not in {1,3,6,12} | Reject | N/A | `valid=False`, `"UNSUPPORTED_HORIZON"` |

### 9.2 Rules

1. **Never silently fall back.** If a model cannot fit, `forecast()` returns `valid=False`, not a degraded approximation.
2. **Never suppress warnings.** All convergence warnings are captured in diagnostics.
3. **Never return negative volatility.** `forecast()` returns `max(prediction, 0.0)` or `valid=False`.
4. **Never impute missing data.** If the input series has gaps, the model receives the gapped series.
5. **Never silently extrapolate diverging GARCH terms.** Non-stationary models report `FORECAST_UNAVAILABLE` for h > 1.

### 9.3 Gap Semantics for Model State / Estimation

Gaps (missing bars in the DatetimeIndex) have different implications depending on model type. The current spec's statement — "if the input series has gaps, the model receives the gapped series" — is too loose. The following rules apply uniformly:

**State-dependent recursive models (GARCH, GJR-GARCH, EWMA):**
A detected gap boundary must not be treated as an ordinary one-step recursion. These models may only fit and forecast across genuinely contiguous 4H stretches. A gap boundary ends one contiguous segment and, if refitting is required, begins a new one. Recursive state must not be propagated across a gap as though it were a normal interval.

Implementation: The `gaps` parameter in `fit()` marks gap boundaries. State-dependent models reset their recursive state at each gap boundary. If the contiguous segment after the last gap is shorter than `min_observations`, the model reports `converged=False` with `warning="insufficient_contiguous_data"`.

**Window-based models (RollingVol, HAR daily/weekly/monthly aggregates):**
If a rolling window's span includes a detected gap, that window position is `NOT_EVALUABLE` — do not compute it as if the observations were evenly spaced. This is the same "insufficient observations → not evaluable, never silently substitute" principle already established for validation block sizes.

Implementation: Features computed over a window that contains a gap boundary produce `NaN` at that position. Models receiving NaN-containing feature vectors handle it per the existing NaN rules.

**Naive:**
The single prior observation used must be the immediately preceding actual observation. If a gap sits between the observation and the forecast origin, flag/exclude per the gap-handling rule Stage 3A already established for target construction. This applies to feature construction as well.

Implementation: NaiveModel accepts the `gaps` parameter. If the most recent observation before `t` is separated by a gap, `forecast()` returns `valid=False` with `diagnostic="GAP_BETWEEN_LAST_OBSERVATION"`.

## 12. Market Simulator — Architectural Capture

**This section is documentation only. No implementation.**

### 12.1 Position in System Architecture

The Market Simulator is a peer core engine, not a sub-component of R2.1:

```
Research Operating System
        │
        ├── Historical Data Engine
        ├── Feature / Target Engine     ← Stage 3A/3B builds this
        ├── Model Engine                ← Stage 3B builds this
        ├── Validation Engine           ← Stage 3C builds this
        ├── Statistical / Monte Carlo Engine
        ├── Market Simulator            ← future core layer, captured here
        ├── Backtest Engine
        ├── Portfolio / Risk Engine
        └── Research Ledger
```

### 12.2 Two Required Modes

1. **Historical reconstruction** — uses observed spread, prices, timestamps, available liquidity proxies, known commissions, documented execution assumptions. Answers: "what would have happened under these specified historical conditions?"

2. **Stochastic market simulation** — randomizes predeclared environmental parameters (spread, slippage, latency, execution delay, fill probability, volatility perturbations, gap behavior, liquidity conditions, execution noise). Answers: "does the strategy remain viable when the market/execution environment is perturbed?"

### 12.3 Conceptual Flow

**Strategy-facing view:**
```
Strategy → standardized Strategy API → Market Simulator/Environment
→ Execution Simulator → Portfolio/Account → Backtest/Research Metrics + Ledger
```

**Environment-stack view:**
```
Historical Data → Market Environment (spread, liquidity, volatility, gaps,
session, latency, slippage, commission, execution rules)
→ Strategy API → Execution Simulator (orders, fills, partial fills,
rejection, latency, slippage)
→ Portfolio/Account (equity, margin, drawdown, exposure, P&L)
→ Backtest/Research Metrics + Ledger
```

### 12.4 Critical Rule

The simulator must never become a mechanism for making a bad strategy look good. Every stochastic parameter must eventually be specified with: source; empirical basis; distribution; bounds; seed; correlation assumptions; reason for inclusion; and which mode it belongs to.

Spread perturbation must derive from an observed historical distribution → a fitted distribution or empirical sampling → a predeclared perturbation range — never "increase spread randomly until the strategy survives."

### 12.5 Interfaces to Capture Now

Stage 3B's model interface is designed with this future consumer in mind:
- Models receive returns (a pd.Series), not raw prices — the simulator will eventually produce simulated returns
- Models return horizon-tagged forecasts — the simulator will eventually produce multiple scenarios
- The model interface is simulation-agnostic; no simulator code enters the model layer

### 12.6 Dependencies to Explicitly Avoid

- No dependency on any single strategy's internals
- No dependency on production NQTS execution code
- No dependency on MT5 bridge or live trading systems
