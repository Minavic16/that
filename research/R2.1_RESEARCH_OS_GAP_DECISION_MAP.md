## 3. WalkForwardEngine / Stage 3C Convergence (Special Focus 1)

### Question: Should Stage 3C be built AS the Research OS's WalkForwardEngine?

**Answer: No. Stage 3C should be built as R2.1-specific evaluation infrastructure in `apparatus/evaluation/`. The common ROS WalkForwardEngine should be built later, after R2.1 validates the pattern.**

### Reasoning:

**3.1 Does the proposed WalkForwardEngine design support fold-relative regime threshold freezing?**

The architecture plan's WalkForwardEngine (§7.5) does NOT mention fold-relative regime thresholds at all. It describes a generic "fit model → record model state → load frozen model" pipeline. The regime classification in the architecture plan is generic (`RegimeBacktestEngine` uses ADX/hybrid/tabfm — all trading-strategy regimes, not volatility terciles).

R2.1's requirement (from `R2.1_CRITICAL_INFRASTRUCTURE_SPEC.md` §B3):
- For each fold: compute volatility terciles from TRAINING data only
- Freeze those thresholds for the fold
- Apply frozen thresholds to OOS observations
- Never recompute from OOS data

This is a **fundamental mismatch**. The architecture plan's WalkForwardEngine has no concept of fold-relative regime thresholds. Adding this would require:
- A regime classification callback/hook in the engine
- Per-fold regime state management
- A "regime source" abstraction (training-derived vs. global vs. external)

This is not a small extension — it changes the engine's core contract.

**3.2 Does it support Partition A / Partition B distinction?**

The architecture plan's WalkForwardEngine (§6.1) describes alternating IS/OOS blocks with Partition A/B structure. However:
- It does not specify that Partition B results must NEVER be labeled "OOS"
- It does not specify the `TEMPORAL_GENERALIZATION_DIAGNOSTIC` label
- It does not specify that Partition B is structurally prevented from being causal OOS

R2.1's requirement (from §G1-G3):
- Partition A: "causal walk-forward OOS" — deployment-relevant
- Partition B: "temporal generalization diagnostic" — NEVER "OOS"
- Partition B results labeled `TEMPORAL_GENERALIZATION_DIAGNOSTIC`

This is a **labeling and contract issue**, not a deep architectural mismatch. A generic engine could support this with proper output tagging.

**3.3 Does it support NOT_EVALUABLE block sizes?**

The architecture plan does NOT mention NOT_EVALUABLE. R2.1's requirement (from §G3):
- If `n_bars / block_size < 3`: block size is NOT_EVALUABLE
- Record as NOT_EVALUABLE in the ledger
- Do not adjust block size to make it pass
- Do not silently skip — report explicitly

This is a **small extension** — add a feasibility check before block processing.

**3.4 Conclusion:**

The proposed WalkForwardEngine in the architecture plan is designed for the **trading-signal domain** (it inherits from BaseEngine, uses BaseSignal, produces P&L-based results). R2.1 needs a **volatility-forecasting evaluator** that:
- Uses `VolatilityModel` protocol (not `BaseSignal`)
- Produces forecast error metrics (not P&L metrics)
- Supports fold-relative regime thresholds
- Labels Partition A/B explicitly
- Handles NOT_EVALUABLE

**These are not the same component.** Building the common WalkForwardEngine first and then retrofitting R2.1's requirements would either:
1. Force the common engine to become domain-specific (defeating its purpose), or
2. Require R2.1 to keep its own evaluation logic anyway (recreating the "3 parallel implementations" problem)

**Recommendation:** Build R2.1's evaluation infrastructure in `apparatus/evaluation/` first. After R2.1 validates the pattern, extract a common WalkForwardEngine for the trading-signal domain. The two share concepts (alternating IS/OOS, fold metadata) but have different domain contracts.

## 4. Portfolio/Account Necessity for R2.1 (Special Focus 2)

### Question: Does R2.1 need equity-curve continuity to reach Stage 3C?

**Answer: No. R2.1 does not need equity-curve continuity, Portfolio/Account design, or any P&L-related infrastructure. This is purely a Strategy 1 / live-trading concern.**

### Reasoning:

R2.1 is a **volatility-forecasting experiment**. Its output is a forecast error metric (RMSE, MAE, QLIKE) per model/horizon/pair/fold. It does NOT:
- Generate trading signals
- Open/close positions
- Produce P&L
- Need position sizing
- Need circuit breakers
- Need equity curves

The architecture plan's §6.3 (Equity-Curve Continuity) and §9.4 (EquityTracker) are irrelevant to R2.1. The plan incorrectly assumes R2.1 is a P&L-generating strategy. It is not.

**Evidence:**
- R2.1's experiment design (`R2.1_EXPERIMENT_DESIGN.md`) specifies MAE, RMSE, QLIKE, direction accuracy — all forecast error metrics
- R2.1's economic evaluation (§185-192) uses Strategy 1's existing signals as a test harness — it does NOT generate its own signals
- R2.1's output classification (§293-309) maps to information categories (Risk Information, Portfolio Information) — not trading performance

**What R2.1 DOES need:**
- Forecast error metrics per fold (RMSE, MAE, QLIKE, R², direction accuracy)
- Per-pair, per-horizon, per-window aggregation
- Block hit rate (fraction of folds where model beats baseline)
- Pair consistency (fraction of pairs with positive effect)
- Regime consistency (fraction of regimes where effect survives)

None of these require equity curves, position sizing, or Portfolio/Account infrastructure.

## 7. Proposed Implementation Sequence

> **This is a PROPOSAL FOR REVIEW, not an authorization to build.**

### Phase A: Model Implementations (Stage 3B deliverables)

Build the 6 volatility models in `apparatus/models/`. Each implements the `VolatilityModel` protocol.

1. `naive.py` — trivial, no dependencies
2. `rolling.py` — trivial, no dependencies
3. `ewma.py` — trivial, no dependencies
4. `garch.py` — depends on `arch` package
5. `gjr_garch.py` — depends on `arch` package
6. `har.py` — OLS regression, no external dependencies

**Gate:** All 6 models pass model contract tests (fit/forecast cycle, causality invariant, horizon handling).

### Phase B: Evaluation Infrastructure (Stage 3C deliverables)

Build the evaluation engines in `apparatus/evaluation/`.

1. `metrics.py` — forecast error metrics (RMSE, MAE, QLIKE, R², direction accuracy, improvement over baseline)
2. `walk_forward.py` — causal walk-forward (Partition A): `walk_forward_evaluate() → WalkForwardResult`
3. `blocked.py` — blocked temporal generalization (Partition B): `blocked_temporal_evaluate() → BlockedResult`
4. Regime classifier — fold-relative training-derived terciles

**Gate:** Walk-forward and blocked evaluation pass causality tests on synthetic data.

### Phase C: Stage 3C Execution

Run the full evaluation across all 20 pairs, 4 horizons, 6 models, 5 block sizes.

**Gate:** All results recorded in ledger. Falsification criteria evaluable.

### Phase D: Statistical Robustness (Stage 3D)

Build bootstrap and Monte Carlo engines. Apply to Stage 3C results.

**Gate:** Statistical significance evaluable.
